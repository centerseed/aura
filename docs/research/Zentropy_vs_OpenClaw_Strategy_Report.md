# Zentropy 競爭策略研究報告：如何在任務規劃上勝過 OpenClaw

**版本**: 1.0
**日期**: 2026-02-09
**基於**: 四個研究團隊的綜合分析（OpenClaw 架構、任務規劃方法論、持續性心理學、AI 規劃 vs 人類規劃）

---

## 一、執行摘要

本報告綜合四個研究方向的發現，回答核心問題：**Zentropy 要如何在任務規劃上做得比 OpenClaw 好？**

**結論**：OpenClaw 是「通用 AI 助手」，什麼都能做但什麼都不專精。Zentropy 應定位為「專業 AI 營運教練」，聚焦三個 OpenClaw 做不到的事：

1. **個人規劃記憶**（Episodic Memory）— 從你的規劃歷史中學習
2. **零摩擦持續性**（Zero-Friction Continuity）— 用心理學設計讓用戶離不開
3. **思考夥伴**（Thought Partner）— 挑戰你的假設，不只執行你的命令

這三樣東西，目前市場上**沒有任何產品**（包括 OpenClaw、Motion、Reclaim、Notion）做到。

## 二、OpenClaw 深度分析

### 2.1 OpenClaw 是什麼？

OpenClaw（前身 Moltbot / Clawdbot）是一個開源、自架的 AI 助手，2026 年初爆紅，達到 **10 萬+ GitHub Stars**，一週內吸引 200 萬訪客。由奧地利工程師 Peter Steinberger（PSPDFKit 創辦人）打造。

### 2.2 核心架構

- **長期運行的 Node.js 服務**，連接聊天平台（WhatsApp、Telegram、Discord）到 AI Agent
- **本地優先（Local-first）**：所有處理在用戶機器上，隱私保障
- **檔案優先（File-first）**：Markdown 檔案作為真實來源
- **50+ 官方整合**：日曆、Email、任務管理、開發工具等

### 2.3 記憶系統

OpenClaw 的記憶系統是其最精密的功能：

| 層級 | 格式 | 用途 |
|------|------|------|
| 持久記憶 | `MEMORY.md` | 決策、偏好、持久事實 |
| 每日筆記 | `memory/YYYY-MM-DD.md` | 當日脈絡、活動、決策 |
| 混合搜尋 | 70% 向量 + 30% BM25 | 語意 + 關鍵字搜尋 |

**儲存**：SQLite + `sqlite-vec` 擴充（向量搜尋）+ FTS5（全文搜尋）

### 2.4 用戶最愛的功能

1. **晨間簡報**（最受歡迎）：每天 7 點自動送天氣、日曆、重要郵件摘要
2. **主動執行**：不只建議，真的去做（發信、建 Kanban、整理檔案）
3. **持久記憶**：跨會話記住脈絡
4. **Cron 排程**：定時自動化（每 30 分鐘檢查信箱、每日研究報告）

### 2.5 致命弱點

| 弱點 | 嚴重程度 | 說明 |
|------|----------|------|
| **高進入門檻** | 🔴 嚴重 | 需要 Docker、CLI、10+ 小時設定，非技術用戶直接放棄 |
| **成本災難** | 🔴 嚴重 | 平均 $200-500/天，有人第一個月花了 $623 |
| **安全漏洞** | 🔴 嚴重 | CVE-2026-25253 一鍵遠端執行，CVSS 8.8；Anthropic 封殺用戶 |
| **留存率低** | 🟡 中等 | 許多人因複雜度試用後放棄 |
| **記憶壓縮問題** | 🟡 中等 | 長會話會「遺忘」，跨專案搜尋有噪音 |
| **無規劃智慧** | 🟡 中等 | 通用記憶，不追蹤估時準確度、不學習規劃模式 |

### 2.6 OpenClaw 的護城河與脆弱性

**護城河**：
- 10 萬+ Stars 社群
- 開源 = 無鎖定
- 本地優先 = 隱私優勢

**脆弱性**：
- 高流失率（試用即放棄）
- 安全醜聞損害聲譽
- 依賴 Claude Opus 4.5+（單一供應商）
- 成本結構：用越多付越多（成功稅）

## 三、任務規劃方法論研究

### 3.1 六大方法論分析

| 方法論 | 核心原則 | #1 失敗原因 | AI 自動化機會 |
|--------|----------|------------|--------------|
| **GTD**（David Allen） | 外部大腦、脈絡執行、每週回顧 | 每週回顧需 60-120 分鐘，太痛苦 | 自動化每週回顧（掃描收件匣、偵測停滯項目） |
| **PARA**（Tiago Forte） | 按可行動性分類（專案/領域/資源/歸檔） | 分類模糊（「健康」是專案還是領域？） | NLU 自動分類（有截止日 → 專案） |
| **時間塊規劃**（Cal Newport） | 每分鐘都有計劃、30 分鐘為單位 | 被打斷就崩潰，整天計劃作廢 | 偵測中斷、自動重新排程 |
| **原則驅動**（Ray Dalio） | 系統化重複決策為演算法 | 需要長期記錄與反思 | 從任務歷史中挖掘模式與原則 |
| **第一性原理**（Elon Musk） | 質疑假設，從基本事實重建 | 需要深度思考能力 | 質疑任務定義（「你真正需要的結果是什麼？」） |
| **OODA 循環**（軍事決策） | 觀察→定向→決策→行動，速度 > 完美 | 分析癱瘓，花太久在觀察/定向 | 即時偵測偏差、自動提議調整 |

### 3.2 規劃系統為何在 2-4 週後被放棄？

**關鍵統計**：
- **92%** 的人在第一個月內放棄行為改變目標
- 習慣養成平均需要 **66 天**（不是流傳的 21 天）
- 生產力 App Day 30 留存率僅 **4.1%**

**七大失敗模式**：

1. **認知過載**（#1 原因）：「打開一堆 App 同步日曆和更新任務清單，還沒開始做事精力就耗盡了」
2. **幻想條件設計**：系統假設穩定精力、零打斷、理想狀態（永遠不會發生）
3. **羞恥螺旋**：漏一天 → 感覺系統「毀了」→ 完全放棄
4. **情緒依賴**：靠「想做事的感覺」驅動，低能量時崩潰
5. **壓力下的摩擦**：「我最忙的時候，工具反而最先崩潰」
6. **維護成本超過價值**：每日維護 > 15 分鐘 → 放棄風險飆升
7. **缺乏新鮮感**：靜態系統 2-3 週後變「隱形」

### 3.3 GTD 的 #1 失敗點：每週回顧

David Allen 認為每週回顧是 GTD 的「關鍵成功因素」，但研究顯示它也是 **#1 放棄觸發點**：

- 需要 60-120 分鐘不被打擾的時間
- 認知負荷極高：回顧所有專案、脈絡、收件匣
- 感覺是「行政負擔」而非生產力
- **跳過一次 → 對系統失去信任 → 放棄**

**Zentropy 的機會**：Coach Agent 自動完成 80% 的每週回顧工作，將 60 分鐘壓縮到 5 分鐘確認。

## 四、持續性與零摩擦的心理學

### 4.1 習慣養成科學

**BJ Fogg 行為模型**：`B = MAP`（行為 = 動機 × 能力 × 提示）

關鍵洞察：**降低「能力」門檻**比提高「動機」更有效。

| 策略 | 說明 | 應用 |
|------|------|------|
| **微小習慣** | 從極小行動開始（2 分鐘以內） | 晨間儀式：「確認今天 3 項優先」（2 分鐘） |
| **錨定行為** | 新習慣綁定既有行為 | 「早餐後 → 打開 Zentropy 看今日預覽」 |
| **慶祝** | 即時正向回饋 | 「完成！今天 3/5 任務已處理」 |

**James Clear 的四法則**：
1. 讓提示明顯（推播晨報通知）
2. 讓行動有吸引力（AI 生成的客製化摘要）
3. 讓行動簡單（< 5 秒完成 Capture）
4. 讓回饋令人滿足（進度條、完成動畫）

### 4.2 蔡加尼克效應（Zeigarnik Effect）

**核心發現**：未完成的任務會持續佔據心理資源，造成焦慮和失眠。

**解決方案**：不需要真的完成任務，只需要**制定計劃**就能釋放心理負擔。

**Zentropy 應用**：
- **晨報**（8:30）：預覽今日開放迴圈 → 建立掌控感
- **晚報**（21:00）：關閉迴圈、為明天制定計劃 → 心理閉合
- **週末**：Coach 主動提議：「要不要把這些延到下週？」→ 許可休息

### 4.3 自我決定理論（Self-Determination Theory）

持續使用需要滿足三個基本心理需求：

| 需求 | 定義 | Zentropy 設計 |
|------|------|--------------|
| **自主性** | 感覺行為是自己選的 | AI 建議而非命令；用戶選擇方法論 |
| **勝任感** | 感覺自己有能力 | 漸進式揭露；每日小勝利 |
| **歸屬感** | 感覺與他人連結 | 「87% 的用戶在 30 天後報告焦慮降低」 |

### 4.4 IKEA 效應

**研究發現**：人們對自己親手打造的東西，估值高出 **63%**。

**Zentropy 應用**：
- 提供 **80% 預設 + 20% 自訂點**
- 第一週：選擇偏好檢視（列表/看板/日曆）
- 第二週：建立第一個自訂篩選器
- 第三週：設定 Areas

**陷阱**：太多 IKEA 效應 = 複雜度爆炸。用戶不該從零開始建造一切。

### 4.5 Duolingo 的留存祕密

Duolingo 透過遊戲化將留存率從 **12% 提升到 55%**：

| 機制 | 效果 | Zentropy 改良版 |
|------|------|----------------|
| 連續天數計數器 | 損失厭惡（Day 7 後生效） | 有，但附「凍結」機制（每月 2 次） |
| 每日目標 | 微承諾 | 靈活：Capture 或 Review 或關閉 1 項 |
| 里程碑慶祝 | 7/30/90 天 | 有意義的成果（「關閉 50 個迴圈」而非「捕獲 100 個任務」） |
| 排行榜 | 社交壓力 | **不採用**（避免罪惡感與社交比較） |

### 4.6 上癮設計 vs 習慣設計

| | 上癮設計（避免） | 習慣設計（採用） |
|---|---|---|
| **獎勵** | 隨機、不可預測（吃角子老虎） | 一致、可預期（完成 = 打勾 + 進度更新） |
| **目標** | 最大化使用時間 | 最大化使用品質 |
| **體驗** | 無限滾動、無終點 | 有界儀式、明確終點（「你今天完成了！」） |
| **通知** | 「你有 12 個逾期任務！！！」| 「準備好規劃今天了嗎？」|

**核心原則**：Zentropy 應讓用戶感覺**「掌控」**（習慣），而非**「被迫」**（上癮）。

## 五、AI 規劃 vs 人類規劃

### 5.1 AI 的超能力

| 能力 | 為何 AI 更強 | 證據 |
|------|-------------|------|
| **模式辨識** | 能即時分析上千筆歷史任務 | 人類會忘記過去的規劃失敗 |
| **無偏差估時** | 使用分佈數據（Outside View） | 人類用 Inside View，陷入規劃謬誤 |
| **依賴映射** | 系統性識別阻礙因素 | 人類忽略隱藏的相依性 |
| **持續校準** | 以完美記憶追蹤實際 vs 預估 | 人類不維護規劃日誌 |
| **最佳化** | 探索上千種排程排列 | 人類「找到第一個可行方案就停」 |

### 5.2 人類不可取代的優勢

| 能力 | 為何人類更強 |
|------|-------------|
| **目標對齊** | 理解深層價值觀與取捨 |
| **情境判斷** | 處理模糊性、政治、人際關係 |
| **策略願景** | 定義「什麼才是成功」 |
| **創意問題解決** | 橫向思考、重新框架問題 |
| **情緒智商** | 感知團隊士氣與動機 |
| **知道何時放棄** | 認知到計劃應該被捨棄而非修補 |

### 5.3 最佳人 AI 分工

| 規劃階段 | 人類角色 | AI 角色 |
|----------|---------|---------|
| **設定目標** | 定義願景、優先級 | 結構化目標、識別衝突 |
| **估時** | 提供初始估計 | 用 Reference Class 校正偏差 |
| **拆解** | 驗證分解是否合理 | 生成完整子任務清單 |
| **排程** | 設定限制條件 | 最佳化日曆分配 |
| **風險評估** | 識別策略風險 | 識別歷史風險模式 |
| **執行** | 做任務、處理例外 | 追蹤進度、發送提醒 |
| **回顧** | 反思什麼重要 | 分析數據（預估 vs 實際） |

### 5.4 規劃謬誤（Planning Fallacy）

**核心發現**（Kahneman 諾貝爾獎研究）：人類長期低估時間和成本 20-50%，即使有經驗也一樣。

**根本原因**：人類的「務實估計」其實是「最佳情境」（零延遲、零障礙）。

**解方：Reference Class Forecasting**
1. 用戶提供初始估計
2. AI 檢索類似的歷史任務
3. AI 計算分佈估計（中位數、75 百分位）
4. AI 套用個人偏差因子
5. AI 呈現：「你的估計 vs 數據驅動估計 vs 建議值」

**目前沒有任何產品實作此功能**。Motion 會排程，但不會質疑你的估時。

### 5.5 市場缺口：沒有產品做到的事

| 缺失功能 | 說明 | 現有產品現況 |
|----------|------|-------------|
| **Reference Class Forecasting** | 用歷史數據對抗規劃謬誤 | 全部沒有 |
| **Episodic Memory** | 從用戶的規劃準確度學習 | 全部沒有 |
| **階層式目標拆解** | 動態多目標分解 | OpenClaw 靠通用 chat，Motion 不支援 |
| **思考夥伴** | 策略推理，挑戰假設 | 全部只做執行 |
| **信任校準** | 用戶控制 AI 自主程度 | 全部是全有或全無 |
| **個人偏差追蹤** | 「你低估設計任務 2.1 倍」 | 全部沒有 |

研究結論：**2025 年的最佳人機協作比例是 70% 人類 / 30% AI**。用戶希望 AI 「提議與建議」，而非完全自動化。

## 六、Zentropy 的致勝策略

### 6.1 核心定位

> **OpenClaw 幫你做事，Zentropy 幫你做對的事。**

OpenClaw = 瑞士刀（什麼都能做，什麼都不專精）
Zentropy = 專業教練（專精規劃與持續性，做到極致）

### 6.2 三大差異化武器

#### 武器一：個人規劃記憶（Episodic Memory for Planning）

**OpenClaw 現況**：有 `MEMORY.md` + daily notes，但只是通用記憶，不追蹤規劃準確度。

**Zentropy 的做法**：

```
用戶：「這個設計任務 2 天可以完成」

Coach（查詢 Episodic Memory）：
「根據你的歷史數據：
 - 過去 10 次設計任務平均花 4.2 天
 - 你對設計任務的低估倍率：2.1x
 - 類似複雜度的任務：3-5 天

 建議：預留 4 天，並在第 2 天安排一次進度檢查。」
```

**技術架構**：
```
Episodic Memory Layer:
├── 每次規劃 + 結果（預估 vs 實際）
├── 按任務類型、複雜度、脈絡索引
└── 檢索相似歷史情境用於新規劃

Semantic Memory Layer:
├── 個人偏差因子（設計 2.1x、開發 1.0x、會議 1.3x）
├── 程序性知識（「外部依賴通常多加 1 週」）
└── 領域啟發法（「API 整合至少 3 天」）
```

#### 武器二：零摩擦持續性（Zero-Friction Continuity）

**OpenClaw 的問題**：它是給工程師用的 CLI 工具，「開始使用」就是巨大摩擦。

**Zentropy 的 90 天留存路線**：

| 階段 | 策略 | 心理學原理 |
|------|------|-----------|
| **Day 1** | 3 分鐘內完成首次 Capture，零設定 | BJ Fogg 微小習慣 |
| **Day 1-7** | 只做 Capture + 晨間預覽（2 分鐘） | 降低能力門檻 |
| **Day 7** | 連續 7 天 → 損失厭惡啟動 | Duolingo 研究：3.6x 完成率 |
| **Week 2-4** | 引入晨報/晚報儀式 | Zeigarnik 心理閉合 |
| **Day 14** | 危機點：主動提議「歸檔舊任務，重新開始」 | Fresh Start Effect |
| **Month 2** | 解鎖自訂功能 | IKEA 效應：63% 更高估值 |
| **Day 30** | 里程碑慶祝 | 「關鍵門檻：留到 30 天的人更可能留到 90 天」 |
| **Month 3+** | 系統消失在日常節奏中 | 自動化習慣（不再需要思考工具） |

**關鍵設計規則**：
- **< 5 秒**：從開啟 App 到完成 Capture
- **< 2 分鐘**：每個儀式（晨報/晚報）
- **< 2 個決策**：每次任務捕獲的決策數
- **零羞恥**：漏一天 → 凍結（不重置），不發罪惡感通知

#### 武器三：思考夥伴（Thought Partner）

**目前所有產品（包括 OpenClaw）都只做 Execution**：你說什麼，它做什麼。

**Zentropy 的 Coach 應該這樣運作**：

```
用戶：「我要兩週內上線這個功能」

OpenClaw：「好的，我幫你排進日曆。」

Zentropy Coach：
「讓我挑戰一下這個假設：

 📊 數據面：
 - 你過去 5 次功能上線平均花 3.5 週
 - 這個功能有 3 個外部依賴（歷史上每個多加 1 週）
 - 下週有 2 個人請假

 🤔 值得思考的問題：
 1. 兩週的 deadline 是硬性的嗎？可以調整嗎？
 2. 可以縮小功能範圍來達成兩週嗎？
 3. 延誤的風險承受度是多少？

 我沒有答案——但這些是值得討論的取捨。」
```

**信任校準介面**（用戶控制 AI 自主程度）：

```
AI 自主設定：
- 排程：高自主（AI 自動排，我每週審查）
- 估時：中自主（AI 建議，我逐項確認）
- 目標優先級：低自主（AI 提供分析，我決定）
- 偏差校正：高自主（AI 自動套用偏差因子）

回饋迴路：
- 「這次估時太高了」→ AI 調整未來校準
- 「這個排程完美」→ AI 強化此方法
```

### 6.3 GTD 自動化：解決最大痛點

Coach Agent 自動完成 GTD 的每週回顧（目前的 #1 放棄觸發點）：

```
每週回顧 Agent（每週日晚上自動運行）：

1. 掃描所有收件匣（Email、筆記、日曆）
2. 識別：
   - 已完成的專案（建議歸檔）
   - 停滯的任務（3 週沒動的待辦）
   - 孤兒項目（沒有下一步行動的專案）
3. 生成 5 分鐘摘要：
   「12 個項目需要定義下一步行動
    3 個專案已完成，建議歸檔
    2 個 Waiting For 項目超過 3 週」
4. 呈現優先化的審查清單（不是完整 dump）

用戶只需：確認/修改，5 分鐘完成。
（對比：手動每週回顧 60-120 分鐘）
```

## 七、建議的 MVP 路線圖

### Phase 1：偏差追蹤儀表板（Wedge Feature）

**為什麼先做這個**：
- 病毒式傳播潛力（「看看你的估時有多不準！」）
- 技術門檻低（只需記錄 估計 vs 實際）
- 立即展示價值

**功能**：
```
你的規劃準確度報告：
- 設計任務：低估 2.1 倍
- 開發任務：準確度 ±15%
- 會議時間：低估 1.3 倍
- 行政任務：高估 1.3 倍

💡 洞察：你在設計任務上持續低估，建議未來自動乘以 2x
```

### Phase 2：Reference Class Forecasting 引擎

- 檢索類似歷史任務 → 計算分佈估計
- 呈現：「你的估計 vs 數據驅動估計 vs 建議值」
- 用戶確認後記錄，持續校準

### Phase 3：階層式規劃 + Episodic Memory

- 高層目標 → 自動拆解子任務（含依賴關係）
- 從歷史中學習：「上次產品上線，這 3 個任務是瓶頸」
- 動態重新規劃（OODA Loop 自動化）

### Phase 4：Thought Partner 模式

- AI 質疑假設、揭露盲點
- 呈現取捨而非答案
- 信任校準介面（每功能自主程度設定）

### Phase 5：團隊規劃 + 共享記憶

- 團隊層級的 Reference Class 數據
- 更多用戶 = 更好的估計（網路效應護城河）

## 九、設計決策框架

設計任何新功能時，問自己這七個問題：

1. **這會減少摩擦還是增加摩擦？**（BJ Fogg）
2. **這能在 2 分鐘內完成嗎？**（James Clear）
3. **這會關閉迴圈還是創造開放迴圈？**（Zeigarnik）
4. **有智慧預設值嗎？**（Thaler Nudge）
5. **這支持用戶自主性嗎？**（SDT）
6. **這會建立習慣還是只是短期使用高峰？**
7. **這是賦能還是剝削？**（倫理設計）

如果任何一個答案有問題，重新設計或砍掉該功能。

## 十、不要做的事（Anti-Patterns）

| Anti-Pattern | 為什麼不做 |
|--------------|-----------|
| **功能膨脹** | 不要加 20 種生產力框架，選 1-2 種（GTD + Time Blocking） |
| **完美資訊謬誤** | 不要試圖捕獲一切，只聚焦可行動項目 |
| **AI 自動駕駛** | 研究顯示過度依賴 AI 會**增加**認知負擔 |
| **複雜 Onboarding** | 首次使用必須 < 2 分鐘 |
| **罪惡感遊戲化** | 避免觸發羞恥螺旋的連續天數/排行榜 |
| **與 OpenClaw 正面競爭** | 不要做通用 AI 助手，專精規劃與持續性 |

## 十一、結論

### 一句話策略

> **OpenClaw 是通用 AI 助手，Zentropy 是專業 AI 營運教練。差異不在能力廣度，而在規劃深度和心理設計。**

### 致勝公式

```
Zentropy = 個人規劃記憶（Episodic Memory）
         + 偏差校正（Reference Class Forecasting）
         + 思考夥伴（Thought Partner）
         + 零摩擦儀式（Zero-Friction Rituals）
```

這四樣東西，**OpenClaw 一個都沒有**。也沒有任何現有產品（Motion、Reclaim、Notion）做到。

### 護城河

1. **規劃記憶**：用越久，估時越準（轉換成本極高）
2. **習慣黏性**：66 天後成為自動行為（不再思考替代方案）
3. **網路效應**：更多用戶 = 更好的 Reference Class 數據

### 最終原則

**為 Day 90 設計，不是 Day 1。**

Day 1 用戶需要的是簡單。Day 90 用戶愛上的是一個消失在日常節奏中的系統——一個根深蒂固的習慣，讓他們不再想工具本身，只想著自己的工作。
