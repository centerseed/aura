# POC 實作分析：規格vs實作的三大落差

## 執行摘要

現有的 Librarian POC 雖然實作了基本的 AI 分類機制，但在三個關鍵維度上與規格產生了落差，導致用戶體驗不理想：

| 問題 | 規格要求 | 現有實作狀態 | 用戶感受 |
|:---|:---|:---|:---|
| **L1 Scope 預期不符** | Area 是身分帽子，禁止濫用 | LLM 無全局上下文，任意創建 Area | AI 「理解錯誤」，需頻繁修正 |
| **修改困難且易失敗** | 不可逆操作需確認，治理應可追溯 | 無確認機制，直接修改DB | 修改後難以回滾，心理焦慮 |
| **邏輯不透明** | 系統應展示推理鏈，用戶可理解 AI 決策 | 推理信息存但未展示，決策黑盒 | 用戶盲目相信/懷疑系統 |

---

## 問題1：AI抓的L1 Scope 很可能跟用戶預期不同

### 現象描述
用戶輸入「和朋友聊天關於創業」，AI 可能：
- **預期 (正確)**：被歸類到 `01_Life` (Self 身分)
- **實際 (錯誤)**：創建新 Area `NewFriendChat` 或歸類到 `02_Work` (因為提到創業)

### 根本原因分析

#### 1.1 LLM 缺乏「身分檔案」(Identity Profile)
**規格要求**（002_Functional_Specification.md 第40-47行）：
```
L1 Area (Identity & Context):
- 核心問題: "我現在戴著哪頂『身分帽子』？"
- 正確範例: Employee, Founder, Self, Expert, Investor
- 錯誤範例: "Work" (太籠統), "Life" (太籠統)
```

**現有實作**（librarian.py 第109-126行）：
```python
agent = self._create_structure_agent(existing_manifest=context_summary)
# context_summary 只包含：
# "- Product: Backend_System (包含: Task1, Task2, ...)"
# "- Product: Finance_Tracking (包含: ...)"
```

**問題**：
- LLM 看不到「用戶的身分邊界」是什麼
- 沒有清晰的「Area 定義清單」
- 對於「和朋友聊天」這類模糊輸入，LLM 無法準確判斷它屬於哪個身分

**具體缺失信息**：
```
❌ 用戶沒有告訴 AI：
   - "我有兩個身分：工程師（02_Career）和創業者（05_Startup）"
   - "個人生活（01_Life）只包括健康、家庭、休閒"
   - "創業相關的事都應該歸到 05_Startup，不要混入 01_Life"
```

#### 1.2 「引力吸附」原則未被有效執行
**規格要求**（librarian.py 第121行）：
```python
"1. **引力吸附 (Semantic Anchoring)**：強烈優先將碎片吸附進上述『現有結構』中。
     除非內容完全不相關，否則禁止建立語義重複的新 L1/L2。"
```

**問題**：
- Prompt 中寫了「優先吸附」，但沒有量化的「禁止條件」
- LLM 對「何時禁止創建新 Area」的邊界不清楚
- 沒有「語義重複檢測」的機制（例如已有 `Coding` Topic，卻又創建 `Programming` Topic）

#### 1.3 簡單輸入容易被誤判
**現象**：
- 輸入：「下午茶，聊天」
- 預期：`01_Life` / `Social` / `Casual`
- 實際可能：創建新 Area `CasualMeetup` 或錯誤地歸到 `02_Work`

**原因**：
- 輸入太短，語義模糊
- LLM 傾向「創建新類別」以避免「錯誤吸附」的風險
- 沒有「最小文本長度」或「上下文擴充」機制

### 解決方向（初步）

1. **建立「用戶身分檔案」(User Identity Profile)**
   - 用戶可主動創建新的 Area 時定義邊界（積極邊界、消極邊界、衝突優先級）
   - 邊界定義存儲在系統中，每次 AI 分類都載入作為決策依據

2. **改進「引力吸附」的決策邏輯**
   ```
   - 優先將新輸入吸附到既有 Area（基於邊界匹配）
   - 只有當新輸入明確超出所有既有 Area 的邊界時，才建議創建新 Area
   - AI 應明確記錄：為什麼需要創建新 Area（而不是勉強吸附）
   ```

3. **實裝「輸入穩定化」流程**
   - 在分類前，先用 Gatekeeper 補充上下文
   - 例如：「和朋友聊天」→「個人生活中的社交活動」

## 問題2：當預期不同後，修改也很麻煩，且一樣很容易失敗

### 現象描述
用戶想修正一個誤分類：
```
原始狀態：任務 "A" 被分類到 Product "Backend_Refactor" (Area: 02_Work)
用戶意圖：移動到 Product "Personal_Learning" (Area: 01_Life)

問題發生的步驟：
1. 用戶說：「把 A 移到個人學習」
2. AI 理解為可能：
   - 新建 Product "Personal_Learning"（在 02_Work Area 下）❌
   - 或者完全誤解，改成其他東西
3. 數據庫直接被修改，用戶看不到中間過程
4. 要改回來，又需要說一次自然語言指令
5. 如果 reclassify_all，整個結構被清空重建，極其危險
```

### 根本原因分析

#### 2.1 無「確認機制」，直接修改數據庫
**規格要求**（002_Functional_Specification.md 第141-144行）：
```python
| **Suggestion (建議)** | 高風險、結構性改變 | move_task_to_product | 需用戶 **Approve** |
| **Auto-Action (自動)** | 低風險、優化性調整 | Create/Merge L3 Topic | 直接執行，但可 Revert |
```

**現有實作**（librarian.py 第308-445行）：
```python
async def execute_governance_instruction(self, instruction: str, user_id: uuid.UUID):
    # ... 直接執行所有 action，無確認
    if act.action_type == "move_task_to_product":
        task.product_id = target_prod.id
        session.add(task)
    await session.commit()  # 👈 直接提交，無回滾機制
```

**問題**：
- 即使是「高風險」操作（如 move_task_to_product），也沒有 approval 流程
- 沒有「Preview」或「Diff」展示修改前後的差異
- `reclassify_all` 直接清空所有數據後重新分類，最高風險

#### 2.2 自然語言理解的風險
**現象**：
```
用戶說：「把 A 移到個人學習」
AI 可能理解為：
  - move_task_to_product: task_id=uuid(A), context="個人學習"
  - 但「個人學習」可能被當作 Product 名稱
  - 或被當作 Topic
  - 或被當作全新的 Area
```

**問題**：
- LLM 的理解具有不確定性
- 沒有「結構化表單」讓用戶明確指定操作
- 用戶無法預測 AI 會如何解釋指令

#### 2.3 修改後無法追溯
**現有實作**：
- 修改被直接寫入 DB
- 沒有「版本歷史」或「操作日誌」
- 如果修改出錯，很難回到之前的狀態

**規格要求**（3.4.4行）：
```python
| **Auto-Action (自動)** | ... | Librarian 直接執行，但在 `Log` 中標記，用戶可於 Review 時 **Revert** |
```

### 解決方向（初步）

1. **建立「Proposal + Approval」流程**
   ```
   AI 分析用戶指令
     → 生成修改提案（Preview 模式）
     → 展示修改前後的對比
     → 用戶確認 ✓ 才提交
   ```

2. **結構化「修改界面」**
   ```
   用戶選擇：
   - 源任務：[Dropdown]
   - 目標 Product：[Dropdown]
   - 目標 Area：[Dropdown]（如需要）

   而不是純文本：「把 A 移到個人學習」
   ```

3. **完整的「操作日誌 + Revert」機制**
   ```
   每次修改被記錄到 governance_log 表
   用戶可以查看修改歷史
   用戶可以「Revert to Version X」
   ```

4. **禁止 `reclassify_all` 作為用戶直接操作**
   ```
   reclassify_all 只能由系統在特定條件下觸發
   如用戶確實需要全量重新分類，應該：
     1. 備份當前狀態
     2. 逐個顯示修改提案（不是一次性清空）
     3. 用戶批准後才執行
   ```

## 問題3：用戶無法感受 AI 是用什麼樣的邏輯在整理

### 現象描述
用戶看到一個分類結果：
```
Title: "Ruby on Rails 性能優化討論"
Area: 02_Work
Product: Backend_System
Topic: Dev

但用戶不知道：
- AI 為什麼把它放在 Backend_System（而不是其他 Project）?
- 相似度是多少？(95%? 60%?)
- 有沒有其他備選方案？
- AI 使用了哪個「治理原則」(熵衰減 vs 高熵保留)?
```

### 根本原因分析

#### 3.1 推理信息存在但未展示
**規格要求**（002_Functional_Specification.md 第120-130行）：
```
第二階段：語義聚合與敘事演化 (Synthesis & Evolution)
- 行動：執行『敘事吞噬』。將判定關聯的碎料內容，透過 LLM 編織進主事件
- 價值：主事件隨時間自發生長
```

**現有實作**（librarian.py 第52-66行）：
```python
class StructuredItem(BaseModel):
    reasoning: str = Field(description="...")
    strategy_used: str = Field(description="Entropy Reduction / ...")
    merged_items: List[str] = Field(description="...")
```

**問題**：
- 這些字段被生成並存儲在 `ai_analysis` JSON 裡
- 但沒有任何 API endpoint 返回這些信息給前端
- 用戶無法看到「為什麼」AI 做這個決定

#### 3.2 缺乏「決策樹」展示
**應該有的內容**：
```
INPUT: "Ruby on Rails 性能優化討論"

決策樹：
├─ 第一步：語義匹配掃描
│  ├─ vs Backend_System: 0.92 ✓ (最高)
│  ├─ vs Frontend_System: 0.34
│  └─ vs Personal_Learning: 0.15
│
├─ 第二步：身分檢測
│  └─ Area = 02_Work (Employee 身分)
│
├─ 第三步：治理原則判定
│  └─ 策略 = 熵衰減 (Entropy Reduction)
│       原因：Backend_System 已有類似主題，執行「敘事吞噬」
│
└─ 第四步：狀態抽屜分配
   └─ Status = 10_active (高變動率)
```

**現有實作**：
- 只有 `reasoning: "..."` 字符串，沒有結構化表達
- 沒有量化的「相似度評分」
- 沒有「備選方案列表」

#### 3.3 沒有「互動式解釋」介面
**用戶應該能做的**：
```
問：「為什麼不放在 Personal_Learning?」
AI 應該能回答：「相似度只有 0.15，且內容中提到『公司專案』」

但現有系統沒有這種對話能力
```

### 解決方向（初步）

1. **建立「推理展示層」**
   ```json
   {
     "item": {
       "id": "xxx",
       "title": "Ruby on Rails 性能優化討論",
       "reasoning_chain": [
         {
           "step": 1,
           "name": "語義匹配掃描",
           "matches": [
             {"product": "Backend_System", "similarity": 0.92, "reason": "核心技術相關"},
             {"product": "Frontend_System", "similarity": 0.34, "reason": "..."}
           ]
         },
         {
           "step": 2,
           "name": "身分檢測",
           "detected_area": "02_Work",
           "confidence": 0.98
         }
       ],
       "strategy": "Entropy Reduction",
       "strategy_reason": "Backend_System 內部高語義緊密度，執行敘事吞噬"
     }
   }
   ```

2. **增加「解釋 API」**
   ```python
   GET /api/items/{id}/explain
   POST /api/items/{id}/challenge
   # 用戶可以挑戰 AI 的決定，系統返回詳細推理
   ```

3. **前端展示「決策透視圖」**
   - 展示相似度評分（圖表化）
   - 展示治理原則應用
   - 展示其他備選方案及其評分
   - 允許用戶點選「我不同意」→ 觸發修改流程

4. **記錄「AI決策版本」**
   ```
   每個分類決策關聯：
   - 使用的 Prompt 版本
   - LLM 模型版本
   - 決策時的上下文信息

   這樣如果 AI 升級，用戶也能理解為什麼重新分類
   ```

## 三個問題的相互關聯

```
問題1 (L1 預期不符)
  ↓
用戶需要修正 (問題2)
  ↓
但看不到 AI 為什麼這樣做 (問題3)
  ↓
只能盲目修改，容易出錯
  ↓
回到問題1（新的修改又預期不符）
```

**形成了一個「焦慮迴圈」**，完全違反了 SAM 系統的「穩定感」目標。

## 核心改進方向：Prompt-Driven 的邊界管理

### 根本認知轉變

**舊思維**：「AI 會亂創建 Area，需要禁止 AI 創建新 Area」

**新思維**：「AI 創建 Area 本身沒問題，問題是 AI 不清楚『什麼時候該吸附、什麼時候該創建』」

**關鍵洞察**：
- Area 的邊界應該由 **用戶定義**（我這個身分的範圍是什麼）
- AI 的職責應該是 **嚴格遵守** 這些邊界，而不是猜測
- 現有 Prompt 缺乏「用戶身分邊界的清晰定義」，導致 AI 面對模糊輸入時傾向保守地創建新 Area（規避錯誤吸附的風險）

### 改進方案：建立「Area 邊界定義」層

#### 核心改進點 1：用戶定義每個 Area 的邊界

每個 Area 不再只是個名稱，而是一個完整的定義檔案，包含：

**定義內容**：
1. **Area 名稱與身分身份**（例如：`02_Employee_CompanyA` = 我在 CompanyA 的工程師身分）
2. **Scope（邊界範圍）**
   - 積極邊界：這個身分應該包含什麼類型的工作/事項
   - 消極邊界：這個身分絕對不應該包含什麼

3. **實例說明**（正例 & 反例）
   - 正例：「和老闆討論功能需求」→ 應屬此 Area
   - 反例：「討論個人健身計畫」→ 不屬此 Area，即使在公司午餐時間

4. **邊界衝突時的優先級**
   - 若輸入同時涉及多個 Area，應該優先選哪個？
   - 例如：「在創業中學到的健身經驗」 → 雖然提到創業，但主要是個人健康話題 → 應屬 `01_Self`

**例子**：
```
Area: 05_Founder_StartupX
身分身份：我作為 StartupX 創辦人的身分
Scope：
  - 積極邊界：
    * 公司戰略與願景
    * 融資與財務管理
    * 團隊招聘與管理
    * 產品開發與市場反饋
  - 消極邊界：
    * 個人身體健康
    * 與朋友的純社交活動（除非涉及商業機會）
    * 在其他公司的工作

實例說明：
  - ✓ 「融資 pitch 新增投資人」→ 屬此 Area
  - ✗ 「晚上和朋友聊創業，但主要在聊健身習慣」→ 屬 01_Self（主題是健身，背景才是創業）
  - ✓ 「和潛在客戶聊產品設計」→ 屬此 Area
  - ✗ 「上班時間看健身視頻」→ 屬 01_Self（內容與創業無關）

邊界衝突優先級：
  若輸入同時提及「創業」和「個人話題」，判定規則為：
  - 判定「主要話題」是什麼（用詞頻率、重點篇幅）
  - 優先依據主要話題歸類
  - 輔助話題記錄在 narrative 中作為上下文
```

#### 核心改進點 2：Prompt 融合「邊界定義」進行決策

當 Librarian 接收新輸入時，Prompt 應包含：

**信息層級**（按優先級排序）：
1. **用戶的 Area 邊界清單**
   - 所有既有 Area 及其完整定義
   - 明確說明每個 Area 的 scope 和衝突解決規則

2. **既有的 Product 與 Topic 列表**
   - 按 Area 組織，方便 AI 進行語義匹配

3. **邊界決策規則**
   ```
   新建 Area 的觸發條件：
   - 用戶明確提到「我有新的身分/角色」（例如「我剛成為投資人」）
   - 新的身分/角色與既有 Area 的邊界無重疊

   吸附到既有 Area 的規則：
   - 若輸入內容符合某個 Area 的「積極邊界」→ 強制吸附
   - 若輸入內容在多個 Area 的「消極邊界」中 → 選主要話題對應的 Area
   - 若有邊界衝突 → 按「邊界衝突優先級」判定
   ```

#### 核心改進點 3：AI 決策邏輯的透明化

Librarian 在分類時應明確記錄：

**決策過程**（結構化記錄）：
1. **邊界匹配掃描**
   - 檢查輸入內容是否符合各個 Area 的「積極邊界」
   - 記錄符合度評分

2. **邊界衝突偵測**
   - 若符合多個 Area，應用「邊界衝突優先級」
   - 記錄衝突解決的理由

3. **吸附決策**
   - 為什麼選擇這個 Area（而不是其他）
   - 是否需要新建 Area（只在明確超越邊界時）

4. **Narrative 補充**
   - 記錄輔助話題和上下文
   - 用戶若質疑決定，可看到「為什麼你只在 narrative 中記錄創業背景」

### 改進前後的對比

**場景：用戶輸入「下午和朋友聊天，聊到創業焦慮和健身習慣」**

#### 改進前（現狀）
```
系統狀態：用戶已創建 Area「01_Self」、「05_Founder_StartupX」

Prompt：「L1 是身分帽子，但沒有邊界定義」
AI 決策：「這涉及創業和個人話題，不確定...建立新 Area『SocialChat』比較安全」
結果：Area = SocialChat_Friends ❌（盲目創建新 Area）
用戶反應：「AI 又理解錯了，為什麼要創建新 Area？」
```

#### 改進後（新方案）
```
系統狀態：用戶已創建 Area：
  - 01_Self：「個人生活、健康、友誼」
  - 05_Founder_StartupX：「創業戰略、融資、團隊」

用戶定義了邊界（或簡單定義）：
  - 01_Self 的消極邊界：不包含工作相關
  - 05_Founder 的消極邊界：不包含純社交

Prompt 接收指令：「用戶有這些 Area 及邊界定義。優先吸附到既有 Area。只有當內容明確超出所有現有 Area 的邊界時，才建議創建新 Area」

AI 決策路徑：
  1. 掃描已有 Area 邊界
  2. 邊界匹配：內容包含「健身」(01_Self) 和「創業焦慮」(05_Founder)
  3. 衝突判定：主要話題是「個人談話」，輔助是「創業背景」
  4. 吸附判定：雖然涉及兩個 Area，但主要內容符合 01_Self 邊界，不需創建新 Area
  5. 決策：Area = 01_Self ✓（根據主要內容和邊界定義）
           Product = Social_Life（既有或新建在 01_Self 下）
           Topic = Casual（既有或新建）
           Narrative：「與朋友的非正式社交，談及個人身心狀態。
                      背景：朋友知曉用戶的創業身分，談話中涉及創業相關焦慮，
                      但核心是個人層面的支持性對話。」

結果：準確分類 ✓，用戶看到「AI 沒有亂創建 Area」✓，決策邏輯清晰 ✓
```

### 這個改進如何解決三個問題

| 原問題 | 改進方案如何解決 |
|:---|:---|
| **L1 預期不符** | 由用戶定義 Area 邊界 → AI 不再盲目猜測 → 首次分類就準確 |
| **修改困難且易失敗** | 首次分類準確度提升 → 修改需求減少 + 用戶理解為什麼分類這樣 → 信心增加 |
| **邏輯不透明** | Prompt 中明確寫出「邊界匹配」「衝突偵測」「優先級應用」 → 用戶可看到決策思路 |

### 實裝思路（不含代碼）

#### 第 1 步：用戶主動創建 Area / Product
- **關鍵轉變**：不是「系統推薦」或「AI 建議創建」，而是 **用戶主動創建**
- 用戶知道自己何時有新的身分/資產，主動在系統中創建
- 創建時可以選擇添加「邊界定義」（Optional but encouraged）
  - 簡模式：只取名字（例如「Personal_Learning」）
  - 詳細模式：定義邊界、積極/消極邊界、衝突優先級

#### 第 2 步：Librarian Prompt 動態加載用戶結構
- 每次 AI 進行新輸入的分類時，加載：
  - 用戶的所有既有 Area 及其邊界定義（若有）
  - 用戶的所有既有 Product 及其簡述
  - 既有的 Topic 分類規範（若有）

- Prompt 邏輯轉變：
  - **不再問「需要新建 Area 嗎？」**而是 **「應該吸附到哪個既有 Area？」**
  - 只有當「明確超出所有既有 Area 的邊界」時，才回報「建議用戶創建新 Area」

#### 第 3 步：AI 專注管控「細項」的分類
- 輸入來臨時，AI 的職責是：
  1. **判定應屬哪個 Area**（基於已有邊界，或根據內容推測）
  2. **判定應屬哪個 Product**（在該 Area 下的語義匹配）
  3. **判定應屬哪個 Topic**（細項工作性質）
  4. **判定狀態抽屜**（Inbox/Active/Maintain/Reference/Archive）

- 此階段 AI 有完整的上下文：
  - 用戶明確定義的邊界（而不是猜測）
  - 用戶已有的結構（Area/Product/Topic 清單）
  - 用戶的命名風格和優先級規則

#### 第 4 步：邊界定義的反向強化
- 當用戶修正 AI 的分類時，系統可建議：
  - 「你把這個項目從 Area A 改到 Area B，這是否表示邊界定義需要調整？」
  - 「你這次修正表明了 Topic X 和 Topic Y 的區別，要更新定義嗎？」
- 系統不是無限學習，而是幫助用戶 **逐步精煉** 自己的結構認知

### 為什麼這個方案有效

1. **權責清晰**
   - **用戶負責**：定義 Area 和 Product（我有什麼身分/資產）
   - **AI 負責**：在既有框架內智慧分類（這個細項屬於哪個資產的哪個工作性質）
   - 不再是「AI 盲目猜測邊界」，而是「AI 在用戶定義的邊界內優化細節」

2. **用戶體驗更好**
   - 用戶創建新 Area 時，心理上已經確認「我確實有這個新身分」
   - 用戶不再經歷「AI 理解錯誤→修改→再次誤解」的焦慮迴圈
   - 只需關注「這個任務細項應該被如何組織」

3. **AI 決策更準確**
   - AI 不需要判斷「該不該創建新 Area」（用戶已決定）
   - AI 只需判斷「在既有的 Area 中，最符合的是哪個 Product/Topic」
   - 上下文清晰 → 決策準確度提升

4. **推理自動透明**
   - AI 在既有邊界內的決策邏輯：邊界匹配 → 優先級應用 → 最終分類
   - 這個過程清晰可解釋，用戶能看到「為什麼選這個 Product」

5. **可持續改進**
   - 用戶不定期回顧自己的 Area/Product 結構，精煉邊界定義
   - 系統可根據用戶的修正建議邊界調整
   - 邊界版本化，用戶能理解「系統邏輯的變化原因」

## 結論

### 問題根源

現有 POC 的問題不是「做不了」，而是 **Prompt 的決策依據不清**：

1. **輸入層**：未能清晰理解用戶的身分邊界 → L1 誤判
2. **過程層**：無確認機制、無透明度 → 用戶信心下降
3. **反饋層**：推理不可見 → 用戶無法學習系統邏輯

### 核心改進策略

與其試圖「修補」這三個層面，更高效的做法是 **根本改變 Prompt 的決策邊界**：

**從「AI 自動判斷邊界」 → 改為「用戶定義邊界，AI 精細管控細項」**

實裝方案：
1. **用戶主動創建 Area / Product**
   - 用戶知道自己有新身分/資產時，主動創建（而不是等待 AI 推薦）
   - 創建時定義邊界（可選但鼓勵）
   - 邊界定義保存在系統中

2. **Librarian 在既有框架內運作**
   - 加載用戶的完整 Area/Product 結構和邊界定義
   - 新輸入來臨時，只判斷「應該吸附到哪個既有框架」
   - 不再判斷「該不該創建新 Area」（用戶已決定）

3. **決策邏輯自動透明**
   - 邊界匹配 → 優先級應用 → 最終分類
   - 用戶可清晰看到「為什麼 AI 選了這個 Area/Product」
   - 決策樹自然從邊界匹配流程中產生

### 改進優勢

1. **大幅減少誤分類**
   - 用戶主動創建 Area/Product → 邊界由用戶確認，不是 AI 猜測
   - AI 只專注細項分類（在既有框架內），準確度提升
   - 用戶修改需求大幅減少，不再有「AI 又理解錯了」的焦慮

2. **自動的推理透明度**
   - 不需要額外的「推理展示 API」
   - 邊界決策過程（邊界匹配 → 優先級應用 → 分類結果）本身就清晰可追溯

3. **權責明確，用戶心理更穩定**
   - 用戶負責「定義我的身分和資產」（Area/Product）
   - AI 負責「組織我的細項」（Topic/Task）
   - 心理模型清晰 → 對系統的預期一致 → 信任提升

4. **持續的邊界精煉**
   - 系統不是無限學習，而是幫助用戶反思邊界定義
   - 用戶修正分類時，系統建議「是否需要調整邊界定義」
   - 邊界版本化，變動時有完整歷史可查

### 實裝優先級建議

1. **首先**：完成「Area 邊界定義 + Prompt 融合」（核心價值）
2. **其次**：補充「邊界決策過程的結構化記錄」（讓推理可見）
3. **再次**：加入「操作日誌 + Approval 流程」（進階穩定性）

這樣的順序確保系統在 **最高價值點** 上先取得突破。

---

*核心洞察：系統的根本問題不在「功能不足」，而在「決策依據不清」。通過讓用戶顯式定義邊界，並讓 AI 嚴格遵守這些邊界，可以同時解決三個表面問題，且自然達成規格中「穩定感」與「透明度」的要求。*
