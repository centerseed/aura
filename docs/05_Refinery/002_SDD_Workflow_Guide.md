# SDD (Spec-Driven Development) 指南：Zentropy 系統開發工作流

本文件詳細定義了 Zentropy 專案所採用的 **規格驅動開發 (SDD)** 方法論。這是一套旨在將 AI 的生成能力與工程的嚴謹性相結合的實作框架。

---

## 一、 核心哲學：規格先行

在 SDD 中，**文檔不是開發後的補償，而是開發前的武裝。**
其核心原則是：**「讓 AI 永遠在上下文充沛、邊界明確、且有法可依的環境下編碼。」**

---

## 二、 四大階段 (The Four Phases)

開發任何功能必須依序通過以下四道「規格閘門」：

### 1. Specify (定義) - [01_Specification]
*   **目標**：明確「做什麼」。
*   **產出**：PRD (商業目標)、FRD (功能的行為邏輯)。
*   **關鍵思考**：如果不做這個功能，創辦人的焦慮會增加嗎？使用者旅程是什麼？

### 2. Plan (計畫) - [02_Plan]
*   **目標**：明確「怎麼做」。
*   **產出**：技術規格書、架構圖、數據結構定義。
*   **關鍵思考**：是否符合 Clean Architecture？Agent 之間如何溝通？

### 3. Tasks (任務) - [03_Tasks]
*   **目標**：定義「步驟」。
*   **產出**：有編號的原子任務清單（Atomic Tasks）。
*   **關鍵思考**：每個任務是否足夠小到讓 AI 精準執行且易於測試？

### 4. Implement (實作) - [Code]
*   **目標**：執行編碼。
*   **產出**：具體的代碼實作與單元測試。
*   **規範**：實作必須與 Tasks 100% 對齊。

---

## 三、 SDD 維護機制：Living Documentation

### 1. 憲法檢查 (Constitution Check)
所有規劃在進入實作前，必須對照 `00_Constitution/constitution.md`。如果 Plan 違反了憲法（例如 Domain 依賴 Infrastructure），則 Plan 必須重寫。

### 2. 決策追蹤 (ADR)
任何導致規格或計畫發生大幅偏轉的決定，必須同步記錄在 `04_ADR` 中，形成系統演進的黑盒子紀錄。

### 3. 計畫合併與歸檔 (Plan Merging)
計畫層包含「全域架構」與「特定功能提案」。
*   **全域架構**：必須持續更新，嚴禁歸檔，它是系統當前的地圖。
*   **功能提案**：在開發完成後，應將關鍵的架構變動（如新的數據欄位、API 介面）**合併 (Merge)** 進全域架構文件，隨後將提案原稿移至 `02_Plan/Archive`。

### 4. 鷹架回收 (Task Archiving)
任務清單 (`03_Tasks`) 是純粹的開發過程記錄。當任務 100% 完成後，清單應立即移至 `03_Tasks/Archive`，以保持工作區清爽。

## 四、 AI 與創辦人的協作模型

| 節點 | 創辦人 (Human) | AI (Zentropy/Antigravity) |
| :--- | :--- | :--- |
| **Specify** | 定義願景與痛點 | 撰寫結構化的 PRD/FRD |
| **Gate 1** | **簽核確認** | - |
| **Plan** | 審核架構合理性 | 生成詳細技術計畫 |
| **Gate 2** | **批准計畫** | - |
| **Tasks** | 檢查邏輯順序 | 拆解原子任務清單 |
| **Implement** | **測試與反饋** | 撰寫代碼並通過測試 |

---

## 五、 如何啟動一個新功能開發？

1.  在 `01_Specification` 建立或更新功能描述。
2.  請 AI 根據 `01` 生成 `02_Plan`。
3.  請 AI 根據 `02` 生成 `03_Tasks/00X_feature_name.md`。
4.  逐一執行 `03_Tasks` 中的任務。
5.  完成後將 Task 移動至 `Archive`，並更新 `Standard` 資料夾。
